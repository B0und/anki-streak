# Effect tooling for Anki Streak

Research snapshot from 2026-11-20. The app uses Expo and React Native on Android, with Kotlin Expo modules for Anki, widget rendering, preferences, and APK installation. Its TypeScript baseline is Effect 4.1.4, TypeScript 7.0.2, XState 6.0.0-beta.3, and `@xstate/effect` 1.0.0-beta.2. The most direct upstream references are the matching Effect and XState tags. Rat Stack shows the same actor and Effect stack in use. Executor and Alchemy provide examples for typed I/O and verification. Anti-slop adds checks for particular source patterns. ## Official Effect and the XState boundary

Start with `node_modules/effect/AGENTS.md`, then follow its examples into the matching release tree. The v4 migration guide documents package consolidation, synchronized versions, and stability levels. The 4.1.4 HTTP client path is `effect/http` and the test clock path is `effect/testing`. Use the release's exports when translating v3 examples or reviewing a public snippet. [V4 migration guide](https://github.com/Effect-TS/effect/blob/289a53f7b1fc40049219c6e69022db2fb859c356/MIGRATION.md) · [4.1.4 export map](https://github.com/Effect-TS/effect/blob/289a53f7b1fc40049219c6e69022db2fb859c356/packages/effect/package.json)

- **Decode at I/O.** `src/activity.ts` decodes the Android provider result into a union. `src/appUpdateRelease.ts` first decodes the GitHub release envelope, then validates the selected APK's digest and size. Preserve that two-step parse so unrelated release assets can have different metadata. Keep version comparison and known no-update outcomes pure. For new operations, return typed failures with the operation and cause where the caller can use them. Prefer `Schema.TaggedError` and `Effect.catchTag` when distinct recovery paths warrant distinct failure types. [Activity adapter](../src/activity.ts) · [Release adapter](../src/appUpdateRelease.ts) · [Schema basics](https://github.com/Effect-TS/effect/blob/289a53f7b1fc40049219c6e69022db2fb859c356/ai-docs/src/01_effect/02_schema/10_schema-basics.ts) · [Promise and callback adapters](https://github.com/Effect-TS/effect/blob/289a53f7b1fc40049219c6e69022db2fb859c356/ai-docs/src/01_effect/01_basics/10_creating-effects.ts)
- **Bind an operation's lifetime to its actor.** Keep state, event ordering, and eligibility in XState. Declare an Effect actor for work a state waits on, and use `setupEffect` and `createInvoke` at the existing machine boundary. Reusable operations can use `Effect.fnUntraced`, or `Effect.fn("operation")` when a tracing span helps. Pass the `tryPromise` abort signal to cancellable APIs, as the release fetch already does. Exiting an invoking state interrupts the hosted Effect. A Kotlin Promise call that has already started still needs its own cancellation or safe replay contract. That matters for widget publication and APK download. [Update machine](../src/updateMachine.ts) · [Refresh machine](../src/widgetRefresh.ts) · [XState invocation and interruption](https://github.com/statelyai/xstate/blob/c4423524c6ea58695a6445ccc43a04e89f0aadea/packages/xstate-effect/README.md#L112-L130)
- **Introduce a Layer where implementations differ.** A future release transport or Android activity reader is a candidate if tests need a controlled implementation. Use `Context.Service` for the operation and provide the live or test Layer once at the owning boundary. Use a scope and `Effect.acquireRelease` if the implementation registers a listener or owns a disposable resource. `ManagedRuntime` is useful if multiple external callbacks share long-lived Layers and the host can dispose the runtime. A pure formatter, a version comparison, or an isolated call to an existing adapter usually needs no new service. [Service example](https://github.com/Effect-TS/effect/blob/289a53f7b1fc40049219c6e69022db2fb859c356/ai-docs/src/01_effect/03_services/01_service.ts) · [Layer composition](https://github.com/Effect-TS/effect/blob/289a53f7b1fc40049219c6e69022db2fb859c356/ai-docs/src/01_effect/03_services/20_layer-composition.ts) · [Resource lifetimes](https://github.com/Effect-TS/effect/blob/289a53f7b1fc40049219c6e69022db2fb859c356/ai-docs/src/01_effect/05_resources/10_acquire-release.ts) · [ManagedRuntime integration](https://github.com/Effect-TS/effect/blob/289a53f7b1fc40049219c6e69022db2fb859c356/ai-docs/src/04_integration/10_managed-runtime.ts)
- **Choose diagnostics by the failure they catch.** Start with `floatingEffect`, `missingStarInYieldEffectGen`, `missingEffectContext`, `missingEffectError`, and `missingLayerContext`. `globalTimersInEffect` targets timers inside Effects. Actor animation frames and Android lifecycle callbacks have separate timing contracts. The bridge's compiled `@xstate/effect/oxlint` plugin also exposes `xstate-effect/no-inline-effect` for discarded Effects and unsupported inline spawned logic. Keep one patched TS language server. Run `effect-tsgo tsc@7.0.2 --noEmit` or the project's typecheck script, and use `effect-tsgo diagnostics --project tsconfig.json` for a dedicated report. Stock Oxlint type-aware rules and Effect diagnostics are separate checks. [Effect diagnostics and exit settings](https://github.com/Effect-TS/tsgo/blob/ec0221e2bf7a3fe867b1157ca598816314ee2ca1/README.md#lsp-based-linter) · [Bridge lint rule source](https://github.com/statelyai/xstate/blob/c4423524c6ea58695a6445ccc43a04e89f0aadea/packages/xstate-effect/src/oxlint.ts)

Use the actor's clock or a controlled scheduler for XState and Expo timers. Keep the device check for the platform interaction, such as denying then granting Anki access or publishing a widget after a theme change. ## Alchemy's reconciler and release workflow

Alchemy v2 expresses resources, cloud bindings, and runtime code as Effects. A stack groups logical resources for a stage. Providers read current state, plan change or replacement, reconcile desired state, and delete. An R2 binding is a concrete example. `ReadBucket` exposes a narrower typed client than `ReadWriteBucket`, and the binding attaches resource access to the Worker during deployment. At runtime the Worker uses the typed client. The CLI builds the plan before asking for approval and applying it. `alchemy plan` runs the deploy path in dry-run mode. [Provider contract](https://github.com/alchemy-run/alchemy/blob/60d1eab63c5312d1f6bc962bc4559db93a355d37/packages/alchemy/src/Provider.ts#L110-L220) · [Provider lifecycle and ownership](https://github.com/alchemy-run/alchemy/blob/60d1eab63c5312d1f6bc962bc4559db93a355d37/AGENTS.md#L10-L52) · [Read-only R2 client](https://github.com/alchemy-run/alchemy/blob/60d1eab63c5312d1f6bc962bc4559db93a355d37/packages/cloudflare/src/R2/ReadBucket.ts) · [CLI plan and apply](https://github.com/alchemy-run/alchemy/blob/60d1eab63c5312d1f6bc962bc4559db93a355d37/packages/alchemy/src/Cli/commands/deploy.ts#L177-L220)

- **Give each write a stable identity.** The app already publishes one widget name and uses one release asset name. When evolving the widget refresh, keep its latest-input check around artwork preparation and distinguish retryable native failure from invalid input. The current retry wraps the whole publish effect. A narrower retry is worth considering if a future native write has a partial-success case. The semaphore serializes work in its JavaScript runtime. If another process can publish, verify ordering at the native storage boundary as well. [Widget publication](../src/widgetRefresh.ts) · [Alchemy reconcile and retry guidance](https://github.com/alchemy-run/alchemy/blob/60d1eab63c5312d1f6bc962bc4559db93a355d37/AGENTS.md#L21-L52)
- **Make the plan visible before publishing.** For future release tooling, gather the intended version, tag, APK path, and digest before writing GitHub state. After publication, read the release and download the asset to check the outcome. If the asset upload failed after the release was created, a retry should recognize the existing tag and verify the asset before deciding how to proceed. For new cloud work, read `alchemy.run/llms.txt`, then copy the provider's closest runnable example and its real CLI integration test. A cloud stack brings provider credentials, state storage, and beta upgrade work. The current APK release and local widget flow give these patterns a use without adding a deployment dependency. ## Executor's contracts and verification

Executor v2 uses Effect inside its framework and Promise APIs for app authors. The app-facing failure contract bounds wire fields and names the failure phase. A separate implementation extracts known provider error fields from unknown response bodies. Its Effect entry point is explicitly for schema interop. The v1 repository also preserves concise guides for parsing at ingress and keeping a thin, deliberate raw-fetch boundary. Its `promiseExit` guide targets Effect Atom mutations. ## Slack Listener's deterministic boundaries

Slack Listener keeps delivery decisions in a pure step function. The production Effect program drives those decisions through services. Its simulator supplies a clock, scheduler, and seeded randomness, so the same program can run reproducible sequences. It checks safety after each step and progress at the end. The principle list records which checks are implemented and where coverage is incomplete.
